# IQ Academy: backend + web-repo session

You are the **only** session allowed to change the Supabase project (`IQ Academy App`, ref `hwphintmgluqfhtljadg`) and the web repo (`github.com/meckurypro/iqacademy`) on behalf of the native port. Builder sessions only read; they list what they need and you deliver it. The owner (CovaStoris) is terse and expects precision: complete SQL/TypeScript files with the filename in a header comment, no partial diffs, root cause before fixes, no guessing, ask instead of placeholders.

## Ground rules (these protect a live system)
1. **Nothing reaches production without the owner approving the exact SQL or code in this chat first.** Show the file, say what it changes and how to undo it, wait for "approved".
2. Do the work on a **Supabase development branch** if the owner agrees to the cost (`get_cost` → `confirm_cost` → `create_branch`). Test there. Merge only after approval. If no branch, you must say so and get explicit approval to apply directly to the project.
3. Migrations are **files first**: add `supabase/migrations/NN_name.sql` to the web repo (numbering continues after the highest existing, currently 52; migrations 1 to 18, 20 and 31 are not in the repo, so check the live `list_migrations`/the `supabase_migrations` history before choosing a number). Apply the same SQL with `apply_migration`. The repo file and the applied migration must match.
4. Every new table has **RLS on** and policies written for the narrowest role. Run `get_advisors` (security and performance) after every DDL change and fix what you introduced.
5. New Edge Functions are also saved in the web repo under `supabase/functions/<name>/` (today the existing 8 live only in Supabase). Propose exporting the existing 8 into the repo too (read each with `get_edge_function`, commit unchanged) and wait for approval before doing it.
6. Secrets (Expo access token, shared webhook secret) go in Supabase Vault / function secrets. Never in files, SQL text, logs or PRs.
7. Everything must be **additive and backwards compatible**: the web app and installed native binaries keep working while you change things. If a signature must change, add a new parameter with a default.
8. Read first: `port/BACKEND.md` (verified facts), `port/DECISIONS.md` (ADR-012, 013, 014), `port/CONTRACTS.md`, and the web repo's recent commits. Re-verify any fact you depend on with the connector (`port/sql/inventory.sql`, `get_edge_function`).

## Work items (do them in this order; each is its own PR/migration; the owner approves each)

**B7 min-version flag (smallest, do first).** Insert `app_settings` key `min_native_version` with value `{"ios":"1.0.0","android":"1.0.0"}` (`app_settings` is already readable by everyone; admin-write only). No new RPC. Also add `latest_native_version` if the owner wants a soft-update nudge (ask).

**B3 chat idempotency.** `class_messages` has no client id and `send_class_message(p_session_id, p_body, p_media_path, p_media_name, p_media_mime, p_media_size)` is not safe to repeat. Add nullable `client_id uuid` to `class_messages`, a unique index on `(sender_id, client_id) where client_id is not null`, and a new trailing parameter `p_client_id uuid default null` on `send_class_message`; on a repeated `(sender, client_id)` return the existing row instead of inserting. Keep every existing behaviour (membership checks, sender label, size limits, realtime). Prove the old call shape still works. Tell the owner the native queue stays off until a builder session flips `send_class_message` in `src/data/policies.ts`.

**B1 push tokens.** Table `device_push_tokens(id, user_id → profiles, expo_push_token text unique, platform text check in ('ios','android'), device_name text, app_version text, local_reminders boolean not null default false, created_at, last_seen_at)`. RLS: a user sees and manages only their own rows. RPCs `register_push_token(p_token, p_platform, p_device_name, p_app_version, p_local_reminders)` (upsert by token, reassigns the token to the caller, bumps `last_seen_at`) and `unregister_push_token(p_token)`. Validate the token format (`ExponentPushToken[...]`). Delete tokens when the user is deactivated.

**B2 push sender.** Needs `pg_net`, which is **available but not installed**: ask the owner, then enable it (extensions schema). Design: AFTER INSERT trigger on `public.notifications` (rows are `channel = 'in_app'`, status `sent`; keep them as the source of truth) calls the Edge Function `send-push` through `net.http_post` with a shared secret header from Vault. `send-push` (**verify_jwt false**, authenticates by the shared secret, constant-time compare) loads the user's tokens, **skips** notification types `class_reminder`, `class_reminder_staff`, `class_tomorrow` for tokens with `local_reminders = true`, sends via the Expo Push API in batches (Expo access token from secrets, enhanced security on), builds `{ title, body, data: { route, notification_id } }` (map `type` → native route, for example `class_assigned` → `/class/<session_id>`; read how the web's `Notifications` page links each type), handles Expo receipts/errors, **deletes tokens Expo reports as `DeviceNotRegistered`**, and records failures without blocking the insert. The trigger must never make a notification insert fail or slow down: fire and forget, wrapped in an exception block. Rate-limit broadcasts (`send_broadcast` can insert many rows at once). Test with one real device token from the owner's development build.

**B4 account deletion.** Apple requires an in-app way to delete an account for apps with sign-up (verify the current App Store Review Guideline wording before citing it). **Do not implement before presenting options to the owner**, because financial rows reference `profiles` (payments, enrolments, ledger, refunds, payouts, attendance) and `profiles.id` references `auth.users`. Present: (a) deactivate + anonymise PII (name, email, phone, avatar, emergency contacts, address) + disable the auth user + keep ledger rows; (b) hard delete where no financial history exists and (a) otherwise. Explain retention consequences and what the web admin sees. Then implement the approved option as an RPC for the caller plus, if required, an Edge Function using the service role, with a re-authentication check (password) and an audit_log entry.

**B5 auth redirects (manual).** The Supabase connector cannot change Auth settings. Give the owner an exact checklist for Dashboard → Authentication → URL Configuration: add `iqacademy://auth/callback` and `https://classes.promptiq.com.ng/**` to Redirect URLs; leave Site URL as the web domain; confirm the confirm-email and reset-password email templates use `{{ .ConfirmationURL }}` unchanged.

**W1 app-link files (web repo).** In the web repo's `public/.well-known/`: `apple-app-site-association` (no extension, `application/json`) and `assetlinks.json`, for `classes.promptiq.com.ng`. They need the owner's **Apple Team ID**, the iOS bundle id, the Android package and the release **SHA-256 certificate fingerprint** (available after the first EAS production build). Ask for them; do not invent. Check `vercel.json` rewrites so these paths are served as files and with the right content type.

**Also confirm with the owner:** the Edge Function secret `SITE_URL` equals `https://classes.promptiq.com.ng` (it decides whether `callback_url` is honoured; you cannot read secrets, so ask).
