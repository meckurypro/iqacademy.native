## Edge Functions (source lives only in Supabase; read it with the connector's `get_edge_function`)
| function | JWT | what native needs to know |
|---|---|---|
| `paystack-init-payment` | yes | POST `{ instalment_id, callback_url? }` → `{ authorization_url, access_code, reference }`. **Returns `reference`.** `callback_url` is honoured only if its origin equals the `SITE_URL` secret, otherwise it silently falls back to `SITE_URL/payment/callback`. Pay instalments in order; older unfinished attempts are marked abandoned |
| `paystack-verify-payment` | yes | POST `{ reference }` → `{ status: succeeded \| pending \| failed \| needs_review }`. **Idempotent, safe to poll.** Already-succeeded payments return `succeeded` without calling Paystack |

| `paystack-create-recipient`, `process-payouts`, `process-refund`, `create-staff-user` | yes | admin-only flows (M10a/M10c); read the source before porting |

## Security review (2026-10-10)
**SEC1 + SEC2, a permission-gate bug found while testing B3 (both fixed and live).** Nine functions plus `send_class_message` guarded themselves with `if not (private.is_admin() or v_s.instructor_id = v_uid [or ...]) then raise 'forbidden'`. On a class with **no instructor assigned** the comparison is NULL, `NOT NULL` is NULL, and the `IF` is silently skipped, so **any signed-in user** passed the gate. Reproduced with a plain student account (every probe in a rolled-back transaction): `complete_session`, `session_attendance_roster` and `session_denied_attempts` ran to completion; `cancel_session`, `end_class_early`, `mark_attendance`, `custom_class_students`, `custom_class_assert_editable` and `generate_checkin_token` bypassed their gate; a student could also post "Instructor <name>" chat messages. **Fix:** treat NULL as false with `coalesce(... , false)` (`port/sql/SEC1_*.sql`, `SEC2_*.sql`). **Verified after:** the same student is `forbidden` on all of them; an admin and the assigned instructor still pass every gate; B3 retries still return the same message id. Rule for all future SQL: never put a nullable comparison directly inside `if not (...)`; use `coalesce(x = y, false)` or `is not distinct from`, and test the *refusal* with a non-privileged account.
Also checked and clean: every callable `SECURITY DEFINER` function that writes data has an authorisation check (`remove_role` and `assign_role` delegate to `private.assert_can_manage_role`); the other `instructor_id = uid` uses are `WHERE` filters or `exists()` (they fail closed).

**Advisors (2026-10-10).** Nothing new from SEC1/SEC2. Pre-existing: ERROR `v_staff_directory` is a SECURITY DEFINER view; WARN leaked-password protection is **off** (Dashboard → Authentication → Password security: worth turning on); WARN six `private` helpers lack a fixed `search_path`; INFO five tables have RLS but no policy by design (PINs, reads, invites are RPC-only). **Review notes on B1/B2/B4 (done by another session; all permissions verified correct).** (1) `register_push_token` defaults `local_reminders` to **true**, which makes `send-push` skip `class_reminder`, `class_reminder_staff` and `class_tomorrow`: a build must pass the real value (true only if it actually schedules local reminders), otherwise reminders are lost. (2) `notify_push` ignores rows whose `send_after` is in the future and nothing pushes them later (none exist today). (3) One HTTP call per notification row: a broadcast to N people makes N calls; fine now, batch if audiences grow. (4) `anonymise_account` does not stop an instructor/coordinator/director with upcoming classes or an unpaid balance from deleting themselves, leaving classes with a deactivated instructor: a product decision. (5) `delete-account` requires the literal `DELETE` but not password re-entry, so an unlocked stolen session could delete the account: M12's step-up auth can close that.


## Refusal tests for B1/B2/B4 (native session, 2026-10-10, rolled-back block, per ADR-018)
As an ordinary signed-in student: `anonymise_account` and `get_push_webhook_secret` are denied (insufficient_privilege); a malformed token or a platform other than ios/android is refused (`invalid_push_token`); a user sees only their own `device_push_tokens` row (a second student sees none), cannot remove someone else's token (it survives), and cannot insert into the table directly. As `anon`: `register_push_token` is denied. The admin refusal of `anonymise_account` (`admin_cannot_delete`) was proven earlier. Nothing persisted (0 tokens, 0 deleted profiles afterwards).
